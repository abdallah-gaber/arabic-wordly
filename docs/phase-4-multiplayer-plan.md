# Phase 4 Multiplayer Plan

## Goal

Add multiplayer play in a way that keeps puzzle fairness server-driven, supports private friend matches first, and leaves room for public matchmaking later.

## Recommended First Multiplayer Version

- Private rooms with short invite codes
- Two players in the same room
- Shared round start generated by the backend
- Real-time sync of guesses, round outcome, and score
- No chat in v1
- Anonymous or lightweight sign-in to reduce friction

## Suggested Technical Shape

1. Add a backend with real-time support.
2. Store rooms, players, rounds, guesses, and scores server-side.
3. Generate the answer on the backend so clients cannot inspect it locally.
4. Send room updates through real-time subscriptions.
5. Keep client UI mostly the same, but read the active puzzle from a multiplayer session instead of local-only storage.

## Good Backend Options

- Supabase: strong fit for PostgreSQL, real-time room updates, and quick Flutter integration
- Firebase: strong fit for rapid prototyping and broad Flutter support
- Custom backend: best only if you already want tighter control over cheating, scaling, and game events

## Data Model To Add

- `profiles`
- `rooms`
- `room_players`
- `room_rounds`
- `room_guesses`
- `room_scores`
- `room_events`

## What Is Needed From Your Side

- Choose the backend stack: Supabase, Firebase, or custom
- Decide the login model: anonymous only, device-based, or Google/Apple sign-in
- Decide whether multiplayer starts as invite-only or also includes public matchmaking
- Approve a small hosting budget if you do not want to stay fully local-only
- Define the score/win rules for multiplayer rounds
- Decide whether daily rooms, ranked rooms, or casual rooms come first
- Decide moderation expectations early if usernames or public rooms are planned

## Recommended Delivery Order

1. Anonymous identity and player profile
2. Private room creation and invite join flow
3. Backend-generated rounds with real-time sync
4. Scoreboard and rematch flow
5. Public matchmaking
6. Ranked or seasonal systems
